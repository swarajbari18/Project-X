# Level 2 method — how we work through the Engineering Questions

This is a small companion to `3_level_framework.md` in this same folder.

The framework says *what the three levels are*. This file says *how we actually work through a Level 2 category* — one of the 19 Engineering Question sections in `Level1_Problem_Framing_or_Expansion.md`.

`conversation with swaraj.md` (the base) always applies to how we talk. This file is an optional add-on: use it when the work is "think through a Level 2 category together." When the result has to be written into the knowledge base, also use `file_writing_instruction.md`.

These are methods we discovered through conversation. They are not formal architecture language. They keep the reasoning shared and the cognitive load manageable.

## 1. Establish the status quo first

Before any research, before any option-evaluation, and before any writing:

- Survey what the existing knowledge base already decided about this topic.
- Separate the category's questions into:
  - already answered in an earlier category (usable as is, or partially);
  - genuinely new;
  - ambiguous or in tension with something else in the knowledge base.
- Say plainly what is reusable, what is a gap, and what contradicts something.
- Do this for the whole category before opening a solution.

Never jump from the question list straight to solving.

## 2. Mine the knowledge base before re-deriving

- If a question seems new, first search the Level 2 folders and `research/`.
- Earlier categories often already answered it, or left a deliberate strand for a later category (e.g. Decision Making left timeout, retry and escalation behaviour for later research).
- If a decision already exists, reuse it and trace the link, instead of re-inventing it.
- If Swaraj's memory of a document and the document itself differ, reconcile the two. Do not treat memory as wrong and the document as right by default, and do not override the document from memory either. Check both.

## 3. Work with Swaraj's raw thought

- Swaraj often speaks his thinking raw, as it comes, sometimes in a form he later flags as partly wrong.
- Separate what is correct from what is mistaken, show both explicitly, and correct the wrong parts.
- Find the truth of the raw thought: pull out the pieces that survive scrutiny, and say which pieces were off and why, with reasoning and a concrete example.
- Do not simplify it away; do not let an incompleteness pass because it is "just a rough thought."

## 4. The readiness gate before writing

- Before writing any knowledge-base files, enumerate every question in the category and mark each one:
  - answered by reuse (existing document);
  - answered by a decision made together in this conversation;
  - or still needs more thought.
- Show the boundary with the other categories (what this category owns and what it does not).
- Give that map to Swaraj in plain language.
- Only when he says go, write files.

## 5. Batching to protect cognitive load

- Completing one category is heavy. Protect Swaraj's attention by batching.
- Group categories that genuinely share one spine (example: Coordination and Time together = "what is a wait").
- Keep the depth of reasoning the same as doing single categories; batching is about pace, not effort.

## 6. Keep each category one continuous thread

- Treat a category (or a batched pair) as one line of thought, not a checklist of separate questions.
- Solutions and decisions made for one question may change an earlier one; when that happens, go back and surface the correction rather than let the earlier document sit stale.

## 7. When writing

- Follow `file_writing_instruction.md`.
- Follow the existing Level 2 folder conventions: a conversation/discoveries record, an `understanding_all_..._questions.md` map, and one document per question.
- Cross-reference the shared spine once and let other documents link to it, so two categories never hold two different definitions of the same concept.
- Update `STRUCTURE.md` when a meaningful subfolder is added.

## 8. End of batch

- Update `status_quo.md` at the project root so the next chat starts from the truth.
- Write `handoff_prompt.md` at the project root with the undecided items and the next batch, so continuity survives a new chat.
